## Read-After-Write Dependencies

Even with split Harvard caches and a double-pumped Register File ([Structural Hazards](/dynamic-courses/computer-architecture/05-pipelined-processor/15-structural-hazards/)), consecutive instructions in real programs rarely operate on independent registers. In our shared calibration loop, `lw t0, 0(s0)` produces `t0` for `addi t1, t0, -128`, which immediately produces `t1` for `add s2, s2, t1`. Whenever a younger instruction attempts to read a source register before an older instruction has written its result back in stage `WB`, a **Read-After-Write (`RAW`) data hazard** threatens to feed stale register data into the ALU unless resolved by **hardware forwarding**, **stall interlocks**, or **compiler scheduling**.

<Divider label="1 · Example" />

### Load-Use and ALU Chain Trace

Consider the four-instruction RISC-V sequence below, which mirrors the Load-Use and ALU accumulation pattern of our calibration loop:

```asm
lw   x1, 0(x2)       # I1: loads x1 at end of MEM (Cycle 4)
add  x3, x1, x4      # I2: reads x1 (distance k = 1 from lw)
sub  x5, x3, x6      # I3: reads x3 (distance k = 1 from add)
or   x7, x1, x8      # I4: reads x1 (distance k = 3 from lw)
```

Compare how a 5-stage pipeline executes these four instructions under two hardware configurations:

1. **Without Forwarding (Stall-Only Interlocks):**
   - $I_1$ (`lw`) commits `x1` to the Register File during the first half of **Cycle 5 (`WB`)**. Because $I_2$ (`add`) would normally enter `EX` in Cycle 4, hardware freezes $I_2$ in `ID` for **2 stall cycles** so $I_2$ reads the updated `x1` in Cycle 5 and enters `EX` in Cycle 6.
   - $I_2$ now reaches `WB` in Cycle 8, forcing $I_3$ (`sub`, dependent on `x3` at distance $k = 1$) to wait **2 more stall cycles** before entering `EX` in Cycle 9.
   - By the time $I_4$ (`or`) reaches `ID` in Cycle 9, `x1` has been in the Register File since Cycle 5 (**0 stalls**). Total execution takes $4 + 4 + (2 + 2) = 12\text{ clock cycles}$.
2. **With Full Hardware Forwarding:**
   - As shown in [the figure](#fig-load-use-hazard), $I_1$ (`lw`) does not obtain `x1` from Data Memory until the **end of Cycle 4 (`MEM`)**, whereas $I_2$ (`add`) needs `x1` at the **start of Cycle 4 (`EX`)**. Forwarding cannot send data backward in time, so the Hazard Detection Unit inserts **1 Load-Use stall bubble**, delaying $I_2$'s `EX` stage to Cycle 5 where `MEM/WB` forwards `x1` (`ForwardA = 01`).
   - $I_2$ (`add`) computes `x3` at the end of Cycle 5 (`EX`) and forwards `x3` directly from `EX/MEM` into $I_3$'s `EX` stage at the start of Cycle 6 (`ForwardA = 10`) with **0 stalls**.
   - $I_4$ (`or`) reads `x1` from the Register File in Cycle 6 (**0 stalls**). Total execution drops to $4 + 4 + 1 = 9\text{ clock cycles}$ ($1$ stall total).

Read-After-Write (`RAW`) hazards can be handled at three increasing levels of sophistication: stalling without bypass hardware, routing results early via hardware forwarding, and—for the single Load-Use case forwarding cannot bridge—freezing 1 cycle in hardware or reordering instructions in the compiler.

### RAW Distance Without Forwarding

In a scalar in-order 5-stage pipeline, only **Read-After-Write (`RAW`)** creates true data hazards: writes always occur in stage `WB` and reads always occur in stage `ID`, so Write-After-Read (`WAR`) and Write-After-Write (`WAW`) hazards cannot arise in order.

Suppose producer instruction $i$ writes destination register `rd` (`rd != x0`) in stage `WB` during Clock Cycle 5, and **hardware forwarding is disabled**. A dependent consumer $i + k$ reading `rd` as `rs1` or `rs2` faces a stall determined strictly by its instruction distance $k$:

| Instruction Distance | Unstalled Consumer `EX` Cycle | Producer `WB` Cycle | Required Stall Bubbles (No Forwarding) |
| :--- | :---: | :---: | :---: |
| **Distance $k = 1$** ($i + 1$) | Cycle 4 | Cycle 5 | **2 stall cycles** (delays `ID` to C5, `EX` to C6) |
| **Distance $k = 2$** ($i + 2$) | Cycle 5 | Cycle 5 | **1 stall cycle** (delays `ID` to C5, `EX` to C6) |
| **Distance $k = 3$** ($i + 3$) | Cycle 6 (`ID` in C5) | Cycle 5 | **0 stall cycles** (split-cycle double-pumping in C5) |
| **Distance $k \ge 4$** | Cycle $\ge 7$ | Cycle 5 | **0 stall cycles** (`rd` already committed) |

### Hardware Forwarding Paths

An arithmetic instruction (`add`, `sub`, `addi`, `and`, `or`, `slt`) computes its 32-bit result at the **end of stage `EX`**—two cycles before stage `WB`. **Hardware forwarding (bypassing)** routes results directly from the interstage pipeline registers (`EX/MEM` and `MEM/WB`) into multiplexers ahead of the functional units so dependent instructions never wait for Register File write-back, as shown in [the figure](#fig-forwarding-paths).

<figure id="fig-forwarding-paths" className="dc-svg-wrap">
  <img src="/dynamic-courses/diagrams/computer-architecture/fig-forwarding-paths.svg" alt="Hardware Forwarding Datapath showing bypass buses from EX/MEM (distance 1) and MEM/WB (distance 2) into the ALU input multiplexers controlled by ForwardA and ForwardB." />
  <figcaption>Hardware forwarding datapath: the Forwarding Unit steers `EX/MEM` (`10`) or `MEM/WB` (`01`) directly into the stage `EX` ALU input multiplexers (`ForwardA` for `rs1`, `ForwardB` for `rs2`).</figcaption>
</figure>

Three forwarding paths cover all register bypasses in the 5-stage pipeline:

1. **`EX/MEM` $\to$ `EX` (`EX` Hazard, Distance $k = 1$, `ForwardA/B = 10`):** Forwards an ALU result produced at the end of `EX` directly to the immediately following instruction's ALU input (`ALU -> ALU` or `ALU -> lw/sw` base address) with **0 stalls**.
2. **`MEM/WB` $\to$ `EX` (`MEM` Hazard, Distance $k = 2$, `ForwardA/B = 01`):** Forwards either an ALU result or a `lw` memory result from `MEM/WB` to the consumer two instructions later with **0 stalls**.
3. **`MEM/WB` $\to$ `MEM` (Store-Data Forwarding):** When an ALU or `lw` instruction produces a value immediately stored by `sw` (`add x8, x3, x2` $\to$ `sw x8, 0(x4)`), `sw` only needs `x8` as its memory write payload (`dataw`) in stage **`MEM`**—not in `EX`—so a bypass from `MEM/WB` into Data Memory's write-data mux resolves the hazard in **0 stalls**.

<Callout type="tip" title="Context: What the Forwarding Unit Wires Check">

Written exam questions do **not** require memorizing formal `if (...)` Boolean syntax, but knowing what the Forwarding Unit wires check explains why edge cases behave the way they do:
- **Match & `RegWrite = 1`:** Forward only if the older stage actually writes a register (`RegWrite = 1`) and its `Rd` matches `ID/EX.Rs1` (`ForwardA`) or `ID/EX.Rs2` (`ForwardB`).
- **`EX/MEM` Priority Over `MEM/WB`:** If both `EX/MEM` ($k = 1$) and `MEM/WB` ($k = 2$) write the same `Rd` (e.g., `addi x1, x1, 1` $\to$ `addi x1, x1, 2` $\to$ `add x4, x1, x5`), **`EX/MEM` (`10`) wins** because it holds the newer value.
- **`Rd != 0` (`x0` Guard):** Writes targeting `x0` (`zero`) are ignored so stale ALU outputs from `addi x0, ...` never overwrite `0`.

</Callout>

### Load-Use Hazard Interlock

While `ALU -> ALU` and `ALU -> lw/sw` dependencies incur **0 stalls** with forwarding, a `lw` instruction only retrieves `Read_Data` at the **end of stage `MEM`**. When the very next instruction ($k = 1$) needs that loaded register at the start of stage `EX`, forwarding cannot send data backward in time.

A **Hazard Detection Unit (HDU)** in stage `ID` monitors whether the instruction currently in `EX` is a load (`ID/EX.MemRead = 1`) whose destination `ID/EX.RegisterRd` ($\neq 0$) matches either `IF/ID.RegisterRs1` or `IF/ID.RegisterRs2`. When a Load-Use conflict is detected, the HDU executes three synchronous actions on the next clock edge to insert **1 stall bubble**:

1. **Zero `ID/EX` Controls:** Forces a multiplexer ahead of `ID/EX` to set `RegWrite = 0` and `MemWrite = 0`, launching a harmless `NOP` bubble into stage `EX`.
2. **Freeze `IF/ID`:** Disables `IF/ID` writing so the stalled consumer repeats `ID` on the next cycle.
3. **Freeze `PC`:** Disables `PC` updating so the instruction after the consumer is re-fetched rather than lost.

One cycle later, the `lw` data sits in `MEM/WB`, and the Forwarding Unit (`MEM/WB -> EX`, `ForwardA/B = 01`) routes it cleanly into the consumer's `EX` stage.

### Zero-Cost Compiler Scheduling

Beyond hardware forwarding, compilers eliminate Load-Use stalls at **zero hardware cost** via **software instruction scheduling**: reordering independent instructions into the delay slot immediately after `lw` while preserving all data and memory dependencies.

Compare computing $A = B + C$ and $D = E - F$ (where `s0` points to `[B, E]`, `s2` points to `[A, D]`, `s1 = C`, `s3 = F`) on a pipeline with full forwarding:

```asm
# Unscheduled (2 Load-Use stalls -> 8 cycles for 6 instructions)
lw   t0, 0(s0)       # Load B
add  t1, t0, s1      # 1 Load-Use stall on t0!
sw   t1, 0(s2)       # Store A
lw   t2, 4(s0)       # Load E
sub  t3, t2, s3      # 1 Load-Use stall on t2!
sw   t3, 4(s2)       # Store D
```

Hoisting the independent `lw t2, 4(s0)` above `add t1, t0, s1` separates each load from its consumer by distance $k = 2$, allowing `MEM/WB` forwarding to supply both `t0` and `t2` with **0 stalls**:

```asm
# Compiler-scheduled (0 stalls -> 6 cycles for 6 instructions, 0 extra gates)
lw   t0, 0(s0)       # Load B
lw   t2, 4(s0)       # Independent load fills t0's Load-Use slot!
add  t1, t0, s1      # t0 forwarded from MEM/WB (0 stalls)
sub  t3, t2, s3      # t2 forwarded from MEM/WB (0 stalls)
sw   t1, 0(s2)       # Store A
sw   t3, 4(s2)       # Store D
```

<Callout type="bridge" title="Compiler Scheduling Versus Out-of-Order Tomasulo Cores">

Embedded RISC-V and ARM Cortex-M microcontrollers rely on static compiler scheduling (`-O2` / `-O3`) because in-order hardware stalls whenever a Load-Use or cache miss occurs. High-performance cores (AMD Zen, Apple M-series) add dynamic **out-of-order execution** (derived from Tomasulo's algorithm with register renaming and a Reorder Buffer): hardware dispatches independent younger instructions around stalled loads at runtime, hiding multi-cycle L1/L2 latencies at the cost of substantial silicon area and power.

</Callout>

<Divider label="3 · Summary" />

| Dependency Pattern | Distance $k$ | Stalls (Forwarding OFF) | Stalls (Forwarding ON) | Active Hardware Mechanism (Forwarding ON) |
| :--- | :---: | :---: | :---: | :--- |
| **ALU to ALU/Memory** | $k = 1$ | $2$ | **$0$** | `EX/MEM` $\to$ `EX` bypass (`ForwardA/B = 10`) |
| **ALU to ALU/Memory** | $k = 2$ | $1$ | **$0$** | `MEM/WB` $\to$ `EX` bypass (`ForwardA/B = 01`) |
| **`lw` $\to$ `ALU` (Load-Use)** | $k = 1$ | $2$ | **$1$** | 1 bubble via `ID/EX.MemRead` + `MEM/WB` bypass (`01`) |
| **`lw` $\to$ `ALU`** | $k = 2$ | $1$ | **$0$** | `MEM/WB` $\to$ `EX` bypass (`ForwardA/B = 01`) |
| **Any `RegWrite` $\to$ Reader** | $k \ge 3$ | **$0$** | **$0$** | Split-cycle Register File double-pumping |

### Data Hazard Resolution Procedure

1. **List Producer-Consumer Pairs:** For each instruction $i$ writing `rd != x0`, scan instructions $i+1, i+2, i+3$ for reads of `rs1 == rd` or `rs2 == rd`.
2. **If Forwarding is OFF:** Assign $2$ stalls for $k = 1$, $1$ stall for $k = 2$, and $0$ stalls for $k \ge 3$ (remembering that an earlier stall shifts downstream instructions later in time, which can widen effective separation!).
3. **If Forwarding is ON:** Assign **$0$ stalls** to all `ALU` producers, and **$1$ stall** exclusively when a `lw` producer is read in `EX` at distance $k = 1$ (**Load-Use**).
4. **Software Rescheduling Check:** To remove a Load-Use stall at zero hardware cost, hoist an independent instruction between `lw` and its consumer, adjusting constant memory offsets if a pointer increment (`addi ptr, ptr, 4`) crosses a `lw`/`sw` using `ptr`.

<Callout type="warning" title="Common Mistakes">

1. **Stalling `ALU -> ALU`:** With full forwarding, `ALU -> ALU` at $k = 1$ or $k = 2$ costs **0 stalls**. Only `lw` at distance $k = 1$ incurs 1 stall!
2. **Double-Counting Stall Cascades:** When instruction $I_2$ stalls for 2 cycles in `ID`, $I_3$ is simultaneously held in `IF` for those same 2 cycles—always track actual cycle numbers (`C1`, `C2`, ...) so you don't double-count stalls that were already absorbed by an earlier stall.
3. **Unadjusted Pointer Offsets:** If you move `addi s0, s0, 4` *above* `sw t1, 0(s0)` during compiler scheduling, you must update the store offset to `sw t1, -4(s0)` so it writes to the original address!

</Callout>

<summary>Reveal Grading Checklist & Model Written Answer</summary>

**Grading Checklist (Full Marks):**
- Definition of **Read-After-Write (RAW)** data hazard (reading an uncommitted register in `ID` before an older instruction commits in `WB`).
- Core idea of **Data Forwarding / Bypassing** (using the result directly from interstage registers `EX/MEM` or `MEM/WB` via multiplexers ahead of the ALU, without waiting for `WB`).
- The bypass paths: `EX/MEM -> EX` ($k = 1$, 0 stalls for ALU producers), `MEM/WB -> EX` ($k = 2$, 0 stalls), and `MEM/WB -> MEM` (store-data bypass for `sw`).
- **Load-Use limit:** `lw` only produces memory data at the end of `MEM`, so a dependent instruction at $k = 1$ requires **1 stall bubble** inserted by the Hazard Detection Unit (freeze `PC`, freeze `IF/ID`, inject `NOP` into `ID/EX`) before `MEM/WB -> EX` forwarding delivers the value.

**Model Written Answer:**
> A **data hazard (RAW — Read-After-Write)** occurs when an instruction in stage `ID` tries to read a source register whose updated value has not yet been written back in stage `WB` by an earlier in-flight instruction. Without forwarding, `k = 1` dependencies require 2 stall cycles and `k = 2` dependencies require 1 stall cycle.
>
> **Data forwarding (bypassing)** avoids waiting for `WB` by routing computed results directly from intermediate pipeline registers into multiplexers at the functional unit inputs:
> - **`EX/MEM` $\to$ `EX` (distance $k = 1$):** Forwards an ALU result computed at the end of `EX` straight to the next instruction's ALU input (`0` stalls).
> - **`MEM/WB` $\to$ `EX` (distance $k = 2$):** Forwards an ALU or load result from `MEM/WB` to the ALU input (`0` stalls).
> - **`MEM/WB` $\to$ `MEM` (store-data forwarding):** Forwards data directly to the Data Memory write port (`dataw`) for a following `sw` (`0` stalls).
>
> Forwarding cannot violate causality in the **Load-Use hazard** (`lw` followed at $k = 1$ by an instruction needing the loaded value in `EX`): `lw` only reads memory at the end of `MEM`, while the consumer needs the operand at the start of `EX`. The **Hazard Detection Unit** therefore inserts **1 stall cycle** (freezing `PC` and `IF/ID` and forcing `NOP` controls into `ID/EX`), after which `MEM/WB -> EX` forwarding resolves the dependency.

</details>

</Exercise>
