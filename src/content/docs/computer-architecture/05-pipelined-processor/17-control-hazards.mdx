## Branch Target Uncertainty

Stage `IF` must supply a new instruction address to `PC` on **every single clock cycle**, yet conditional branches—such as `bne s0, s1, loop` at the bottom of our calibration loop ([Control Flow Translation](/dynamic-courses/computer-architecture/03-riscv-instructions/09-control-flow/))—do not immediately know two pieces of information during `IF`: **whether the condition holds** (taken vs. untaken) and **where to jump** ($\text{Target} = \text{PC} + \text{Imm}$). This gap between fetching a branch and resolving its outcome creates a **control hazard**, penalizing $\text{CPI}_{\text{pipe}}$ whenever wrong-path instructions must be stalled or flushed.

<Divider label="1 · Example" />

### Loop Branch Penalty Comparison

Suppose a benchmark contains $f_{\text{branch}} = 20\%$ conditional branches (such as `bne s0, s1, loop`), of which $p_{\text{taken}} = 65\%$ are **taken** (jumping back to `loop`) and $35\%$ are **untaken** (falling through to $\text{PC} + 4$). Under the standard **Predict-Untaken** policy, stage `IF` continues fetching sequentially along $\text{PC} + 4$ without pausing:

- Whenever a branch is **untaken** ($35\%$ of branches), the sequential instructions already fetched behind it are valid $\implies \mathbf{0\text{ stall cycles}}$.
- Whenever a branch is **taken** ($65\%$ of branches), the sequential instructions fetched before the branch resolves are wrong-path instructions that must be **flushed** (turned into `NOP` bubbles), costing $P_{\text{stage}}$ cycles depending on where the microarchitecture resolves branches ([the figure](#fig-branch-resolution-stages)):

<figure id="fig-branch-resolution-stages" className="dc-svg-wrap">
  <img src="/dynamic-courses/diagrams/computer-architecture/fig-branch-resolution-stages.svg" alt="Branch penalty across pipeline resolution stages: resolving in ID incurs a 1-cycle penalty (flushing IF); resolving in EX incurs a 2-cycle penalty (flushing IF and ID); resolving in MEM incurs a 3-cycle penalty (flushing IF, ID, and EX)." />
  <figcaption>Taken-branch flush penalty across resolution stages: resolving in `ID` flushes 1 instruction (`IF`), resolving in `EX` flushes 2 instructions (`IF`, `ID`), and resolving in `MEM` flushes 3 instructions (`IF`, `ID`, `EX`).</figcaption>
</figure>

Evaluating $\text{Stalls}_{\text{ctrl}} = f_{\text{branch}} \times p_{\text{taken}} \times P_{\text{stage}}$ across the three hardware designs gives:

1. **Early `ID` Resolution** ($P_{\text{ID}} = 1$): $\text{Stalls}_{\text{ctrl}} = 0.20 \times 0.65 \times 1 = 0.13\text{ cycles/instr}$.
2. **Baseline `EX` Resolution** ($P_{\text{EX}} = 2$): $\text{Stalls}_{\text{ctrl}} = 0.20 \times 0.65 \times 2 = 0.26\text{ cycles/instr}$.
3. **Late `MEM` Resolution** ($P_{\text{MEM}} = 3$): $\text{Stalls}_{\text{ctrl}} = 0.20 \times 0.65 \times 3 = 0.39\text{ cycles/instr}$.

By contrast, if the processor disables prediction completely and uses a **Stall-Always** policy (*solo stalli* — freezing `IF` as soon as a branch is detected until `EX` finishes), **100% of branches** pay the $2$-cycle delay regardless of outcome: $\text{Stalls}_{\text{ctrl}} = 0.20 \times 1.00 \times 2 = 0.40\text{ cycles/instr}$.

<Divider label="2 · Theory" />

Below, we derive why the branch flush penalty equals $s - 1$ cycles for resolution at stage index $s$, show how synchronous clear lines neutralize speculative instructions, compare Stall-Always against branch prediction policies, and pinpoint when preceding `ALU` dependencies trigger an extra `ID` comparison stall.

### Resolution Stage Penalties

Why does resolving a branch at pipeline stage index $s \in \{2, 3, 4\}$ (`ID = 2`, `EX = 3`, `MEM = 4`) always carry a misprediction flush penalty of $P_{\text{stage}} = s - 1$ cycles? If a branch enters `IF` in Cycle $1$, it reaches stage $s$ in Cycle $s$, so the correct target address $\text{PC} + \text{Imm}$ can only be fetched in Cycle $s + 1$—leaving exactly $s - 1$ intervening fetch cycles (`Cycle 2` through `Cycle s`) filled with wrong-path instructions:

- **Stage `EX` Resolution** ($s = 3$, $P_{\text{EX}} = 2$): Standard RISC-V datapath where the `EX` branch adder computes $\text{PC} + \text{Imm}$ and the main ALU tests `rs1` vs. `rs2` in Cycle 3. Taken branches flush `IF` and `ID` ($2$ bubbles).
- **Stage `MEM` Resolution** ($s = 4$, $P_{\text{MEM}} = 3$): Microarchitectures that latch the ALU comparison flag into `EX/MEM` before routing `PCSrc` during Cycle 4 (`MEM`). Taken branches flush `IF`, `ID`, and `EX` ($3$ bubbles).
- **Stage `ID` Resolution** ($s = 2$, $P_{\text{ID}} = 1$): Hardware moves both the 32-bit target adder ($\text{PC} + \text{Imm}$) and a dedicated fast comparator (`rs1 == rs2` XOR-tree for `beq`/`bne`) directly into stage `ID`. Taken branches flush only the single instruction in `IF` ($1$ bubble), cutting branch penalty in half compared to `EX`—at the cost of a dedicated comparator and an extra RAW hazard check in `ID`.

### Synchronous Pipeline Flush

When the pipeline predicts untaken along $\text{PC} + 4$ and a branch later evaluates as **taken**, those $s - 1$ speculative instructions already sitting inside `IF/ID` (and `ID/EX`, `EX/MEM` for later resolution) must be neutralized before they modify registers or memory. As shown in [the figure](#fig-pipeline-flush), the Branch Unit asserts synchronous clear lines (`IF.Flush`, `ID.Flush`) that zero the instruction / control fields (`RegWrite = 0`, `MemWrite = 0`), turning wrong-path instructions into `NOP` bubbles while multiplexing `Target` into `PC`.

### Branch Policies and Predictors

Besides resolving branches earlier in `ID`, four prediction or scheduling strategies reduce how often flushes happen (the first two are directly tested in exam CPI calculations; dynamic predictors and delay slots explain how real CPUs push penalties toward zero):

1. **Stall-Always** (*Solo Stalli*): Freeze `IF` immediately upon detecting a branch until its outcome and target resolve. Simple to build, but penalizes **every** branch whether taken or untaken:
   $$\text{Stalls}_{\text{ctrl,stall}} = f_{\text{branch}} \times 1.0 \times P_{\text{stage}}$$
2. **Static Prediction:**
   - **Predict-Untaken:** Speculate along $\text{PC} + 4$, paying $0$ stalls when untaken and $P_{\text{stage}}$ flushes when taken:
     $$\text{Stalls}_{\text{ctrl,untaken}} = f_{\text{branch}} \times p_{\text{taken}} \times P_{\text{stage}}$$
   - **Predict-Taken:** Only helps if the target $\text{PC} + \text{Imm}$ is known before the condition; without a target cache in `IF`, Cycle 1 still does not know where to jump.
3. **Dynamic Branch Prediction:** Real CPUs use small `PC`-indexed tables in `IF`—a **2-bit saturating counter** (*Strongly/Weakly Taken vs. Untaken*, needing two consecutive mispredictions to flip, so nested loops only mispredict on exit rather than exit + re-entry) paired with a **Branch Target Buffer** (BTB) caching the target address so predicted-taken branches jump with **0 stalls**.
4. **Delayed Branching:** Older ISAs forced $1$ **branch delay slot** after every branch that executes unconditionally while the branch resolves (filled by compiler scheduling; omitted from modern RISC-V because it complicates wide superscalar cores).

### ALU-to-Branch Interaction Rules

Look at the final two instructions of our shared calibration loop:

```asm
addi s0, s0, 4       # I4: computes new s0 at end of EX
bne  s0, s1, loop    # I5: compares s0 against s1!
```

Whether this distance-1 `ALU(i) -> Branch(i+1)` dependency adds an extra RAW stall depends on **branch resolution stage**:

1. **Resolved in `ID`** ($\implies +1\text{ Extra Stall}$):
   - $I_4$ (`addi`) enters `IF` in Cycle 1, `ID` in Cycle 2, and **`EX` in Cycle 3**.
   - $I_5$ (`bne`) enters `IF` in Cycle 2 and **`ID` in Cycle 3**.
   - During Cycle 3, `bne` needs `s0` inside the `ID` comparator at the *exact same clock cycle* `addi` is still computing `s0 + 4` inside `EX`! Even with an `EX/MEM -> ID` forwarding bus, the ALU output is not latched until the end of Cycle 3. The Hazard Detection Unit must insert **1 RAW stall cycle** so `addi` reaches `EX/MEM` in Cycle 4, forwarding `s0` into `ID` in Cycle 4. (By the same logic, `lw(i) -> Branch(i+1)` at distance $k = 1$ with `ID` branch resolution costs **2 RAW stall cycles**!)
2. **Resolved in `EX` or `MEM`** ($\implies 0\text{ Extra Stalls}$):
   - When `bne` evaluates its comparison inside **`EX` (Cycle 4)**, `addi` has already advanced to **`MEM` (Cycle 4)**, so standard `EX/MEM -> EX` forwarding (`ForwardA = 10`) delivers `s0` at the start of Cycle 4 with **0 extra stalls**!
   - When `bne` resolves in **`MEM` (Cycle 5)**, `addi` is in **`WB` (Cycle 5)**, again delivering `s0` via forwarding with **0 extra stalls**!
   - Any problem statement mentioning *"X% of Branch instructions depend on a preceding ALU instruction"* when branches resolve in **`EX` or `MEM`** with forwarding enabled is a **pure decoy**—never add a stall for it!

<Callout type="bridge" title="Branchless Saturation in Real-Time Control Firmware">

In $1\text{ kHz}$ motor and flight control loops, data-dependent `if/else` clamps (such as actuator saturation `if (u > u_max) u = u_max;`) suffer unpredictable flush penalties whenever noisy sensor spikes flip branch outcomes. Firmware engineers replace short unpredictable branches with branchless arithmetic or conditional-select sequences so every control tick executes a fixed, flush-free cycle count.

</Callout>

### Control Penalty Procedure

1. **Identify Resolution Stage:** Map the stated resolution stage to its wrong-path penalty: `ID` $\to 1$, `EX` $\to 2$, `MEM` $\to 3$.
2. **Check Branch Policy:**
   - **Predict-Untaken:** Multiply $f_{\text{branch}} \times p_{\text{taken}} \times P_{\text{stage}}$ (untaken branches cost $0$ stalls).
   - **Stall-Always** (*Solo Stalli*): Multiply $f_{\text{branch}} \times 1.0 \times P_{\text{stage}}$ (ignore $p_{\text{taken}}$ completely!).
3. **Check `ALU -> Branch`:** Add $f_{\text{ALU}\to\text{Branch}} \times 1$ **if and only if** branches resolve in stage **`ID`** (and notice that this RAW comparison stall occurs before the condition is known, affecting all such dependent branches whether taken or untaken). Ignore `ALU -> Branch` completely if branches resolve in `EX` or `MEM`.

<Callout type="warning" title="Common Mistakes">

1. **Applying $p_{\text{taken}}$ Under *Solo Stalli*:** When a problem specifies *"usare solo stalli nella gestione dei branch"* (no prediction), **every** branch stalls—even if the prompt also mentions *"60% taken"* as a distractor! Use $1.0$, not $0.60$.
2. **Counting `EX`/`MEM` Branch Decoys:** Never add $+1$ stall for `ALU(i) -> Branch(i+1)` when branches resolve in `EX` or `MEM` with forwarding active.
3. **1-Bit vs. 2-Bit Predictors:** An inner loop iterated $N$ times inside an outer loop mispredicts **twice** per inner-loop run with a 1-bit predictor (exit + next entry), versus **once** per run (exit only) with a 2-bit saturating counter.

</Callout>
