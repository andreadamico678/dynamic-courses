## Additive Cycle Penalty Accounting

Chapters 14–17 isolated each pipeline timing and stall mechanism one by one: slowest-stage clock period $T_{\text{clk,pipe}}$ ([Five-Stage Pipeline](/dynamic-courses/computer-architecture/05-pipelined-processor/14-five-stage-pipeline/)), unified-memory port stalls ([Structural Hazards](/dynamic-courses/computer-architecture/05-pipelined-processor/15-structural-hazards/)), RAW and Load-Use bubbles ([Data Hazards and Forwarding](/dynamic-courses/computer-architecture/05-pipelined-processor/16-data-hazards/)), and branch resolution flushes ([Control Hazards and Branching](/dynamic-courses/computer-architecture/05-pipelined-processor/17-control-hazards/)). On a real workload, all three hazard classes occur concurrently, raising the ideal steady-state throughput ($\text{CPI}_{\text{ideal}} = 1$) to an effective **pipelined Cycles Per Instruction** $\text{CPI}_{\text{pipe}}$ that plugs directly back into $T_{\text{exec}} = \text{IC} \times \text{CPI}_{\text{pipe}} \times T_{\text{clk}}$.

### Multi-Hazard Pipeline CPI Audit

Evaluate $\text{CPI}_{\text{pipe}}$ for a 5-stage RISC-V processor with **unified single-port memory**, **full hardware forwarding**, and **Predict-Untaken** branch resolution in stage **`EX`**, executing a benchmark with instruction mix:

- **`ALU`:** $60\%$
- **`Load` (`lw`):** $14\%$
- **`Store` (`sw`):** $10\%$
- **`Branch`:** $16\%$ (of which $50\%$ are **taken**)

Runtime profiling reports three data-dependency frequencies:

- $30\%$ of `ALU` instructions depend on the immediately preceding `ALU` instruction ($k = 1$).
- $25\%$ of `ALU` instructions depend on an immediately preceding `Load` instruction ($k = 1$).
- $30\%$ of `Load` instructions compute their base address from the immediately preceding `ALU` instruction ($k = 1$).

As depicted in [the figure](#fig-pipeline-cpi-breakdown), we sum the ideal baseline rate ($1.00$) with each active stall category while discarding zero-penalty forwarding paths:

  <img src="/dynamic-courses/diagrams/computer-architecture/fig-pipeline-cpi-breakdown.svg" alt="Additive decomposition of pipeline Cycles Per Instruction (CPI_pipe): baseline 1.0 plus structural stalls (unified memory), data stalls (Load-Use bubbles), and control stalls (branch flushes)." />
  <figcaption>Additive decomposition of $\text{CPI}_{\text{pipe}}$: baseline $1.00$ cycle/instruction stacked with structural, data, and control stall contributions.</figcaption>
</figure>

1. **Baseline Rate:** $\text{CPI}_{\text{base}} = 1.00$.
2. **Structural Hazards (Unified Memory):** Every `Load` ($14\%$) and `Store` ($10\%$) stalls stage `IF` for $1$ cycle during `MEM`:
   $$\text{Stalls}_{\text{struct}} = (0.14 + 0.10) \times 1 = 0.24\text{ cycles/instr}$$
3. **Data Hazards (Full Forwarding Active):**
   - `ALU -> ALU` ($30\%$ of `ALU`) resolves via `EX/MEM` bypass $\implies 0\text{ stalls}$.
   - `ALU -> Load` ($30\%$ of `Load`) forwards the base register from `EX/MEM` into `lw`'s `EX` address calculation $\implies 0\text{ stalls}$.
   - `Load -> ALU` at $k = 1$ ($25\%$ of the $60\%$ `ALU` instructions) triggers a **1-cycle Load-Use bubble**:
     $$\text{Stalls}_{\text{data}} = 0.60 \times 0.25 \times 1 = 0.15\text{ cycles/instr}$$
4. **Control Hazards (Predict-Untaken in `EX`, $P_{\text{EX}} = 2$):** Only taken branches ($50\%$ of $16\%$) flush `IF` and `ID`:
   $$\text{Stalls}_{\text{ctrl}} = 0.16 \times 0.50 \times 2 = 0.16\text{ cycles/instr}$$

Summing all terms yields the exact effective CPI:

$$\text{CPI}_{\text{pipe}} = 1.00 + 0.24 + 0.15 + 0.16 = 1.55\text{ cycles/instr}$$

### Master Pipeline CPI Equation

In steady state ($\text{IC} \gg 5$), a scalar 5-stage pipeline retires one instruction per cycle minus every cycle lost to stall bubbles or wrong-path flushes. Because each hazard event $i$ occurs on a fraction $f_i$ of dynamic instructions and injects $\text{Penalty}_i$ bubble cycles, effective pipelined CPI expands linearly:

$$\text{CPI}_{\text{pipe}} = 1 + \sum_{i} \left(f_i \times \text{Penalty}_i\right) = 1 + \text{Stalls}_{\text{struct}} + \text{Stalls}_{\text{data}} + \text{Stalls}_{\text{ctrl}}$$

Substituting $\text{CPI}_{\text{pipe}}$ and the pipelined clock period $T_{\text{clk,pipe}} = \max_j(t_{\text{stage},j}) + t_{\text{setup}} + t_{\text{cq}}$ into the [CPU Performance Equation](/dynamic-courses/computer-architecture/02-computer-performance/06-cpu-performance-equation/) links microarchitectural stalls directly to wall-clock runtime and real speedup over a single-cycle processor ($\text{CPI}_{\text{single}} = 1$):

$$T_{\text{exec,pipe}} = \text{IC} \times \text{CPI}_{\text{pipe}} \times T_{\text{clk,pipe}}, \qquad S = \frac{T_{\text{exec,single}}}{T_{\text{exec,pipe}}} = \frac{1 \times T_{\text{clk,single}}}{\text{CPI}_{\text{pipe}} \times T_{\text{clk,pipe}}}$$

Notice how hazards erode ideal speedup by the exact factor $1 / \text{CPI}_{\text{pipe}}$.

### Producer Versus Consumer Percentages

The single most frequent numerical error in pipeline evaluations is multiplying a conditional dependency percentage by the wrong instruction-class frequency. Always check grammatical ownership of the percentage:

1. **Consumer-Relative Phrasing:** *"25% of **ALU instructions** depend on an immediately preceding Load"* ($P(\text{Load-Use} \mid \text{ALU}) = 0.25$). Multiply by the **consumer** class frequency $f_{\text{ALU}}$:
   $$f_{\text{load-use}} = f_{\text{ALU}} \times 0.25$$
2. **Producer-Relative Phrasing:** *"30% of **Load instructions** are immediately followed by a dependent ALU instruction"* ($P(\text{Load-Use} \mid \text{Load}) = 0.30$). Multiply by the **producer** class frequency $f_{\text{Load}}$:
   $$f_{\text{load-use}} = f_{\text{Load}} \times 0.30$$
3. **Global-Stream Phrasing:** *"5% of **all executed instructions** stall on a Load-Use hazard."* The fraction is already normalized to $\text{IC}$ ($f_{\text{load-use}} = 0.05$)—never multiply by $f_{\text{Load}}$ or $f_{\text{ALU}}$ a second time!

### Worked Configuration Patterns

Once you know the master equation and conditional percentage anchoring, every written CPI problem is simply a combination of hardware switches (memory topology, forwarding on/off, branch stage, and branch policy). The two patterns below show the exact switches that flip terms on exams:

- **Case 1 — Split Memories, Forwarding Disabled, Stall-Always (*Solo Stalli*) in `ID`:**
  Suppose a workload has `Load` $18\%$, `Store` $12\%$, `Branch` $15\%$ ($40\%$ taken), and `ALU` $55\%$. Without forwarding, $30\%$ of `ALU` depend on a preceding instruction at distance $k = 1$ ($2\text{ stalls}$), $15\%$ of `ALU` depend at distance $k = 2$ ($1\text{ stall}$), and $30\%$ of `Load` depend on an `ALU` address producer at distance $k = 1$ ($2\text{ stalls}$).
  - $\text{Stalls}_{\text{struct}} = 0$ (split Harvard memories).
  - $\text{Stalls}_{\text{data}} = (0.55 \times 0.30 \times 2) + (0.55 \times 0.15 \times 1) + (0.18 \times 0.30 \times 2) = 0.33 + 0.0825 + 0.108 = 0.5205$.
  - $\text{Stalls}_{\text{ctrl}} = 0.15 \times 1.00 \times 1 = 0.15$ (*solo stalli* stalls $100\%$ of branches; $40\%$ taken is unused!).
  - $\text{CPI}_{\text{pipe}} = 1.00 + 0 + 0.5205 + 0.15 = 1.6705\text{ cycles/instr}$.

- **Case 2 — Unified Memory, Forwarding Active, Late `MEM` Branch With Decoy Dependency:**
  Suppose a workload has `Load` $16\%$, `Store` $12\%$, `Branch` $12\%$ ($50\%$ taken), and `ALU` $60\%$, with unified memory, full forwarding, and Predict-Untaken resolving branches in stage **`MEM`** ($P_{\text{MEM}} = 3$). Profiling states: $30\%$ of `ALU` depend on `ALU` ($k = 1$), $35\%$ of `ALU` depend on `Load` ($k = 1$), and **$50\%$ of `Branch` depend on the preceding `ALU` instruction ($k = 1$)**.
  - $\text{Stalls}_{\text{struct}} = (0.16 + 0.12) \times 1 = 0.28$.
  - $\text{Stalls}_{\text{data}} = 0.60 \times 0.35 \times 1 = 0.21$ (`ALU -> ALU` costs $0$).
  - `ALU -> Branch` Check: Because branches resolve in **`MEM`** (not `ID`), forwarding supplies the `ALU` operand with **$0$ extra stalls**—the $50\%$ figure is a **decoy**!
  - $\text{Stalls}_{\text{ctrl}} = 0.12 \times 0.50 \times 3 = 0.18$.
  - $\text{CPI}_{\text{pipe}} = 1.00 + 0.28 + 0.21 + 0.18 = 1.67\text{ cycles/instr}$.

<Callout type="bridge" title="Hard Real-Time Instruction Budgets">

When deploying a $1\text{ kHz}$ ($T_{\text{deadline}} = 1.0\text{ ms}$) state-estimation filter on a $168\text{ MHz}$ ($T_{\text{clk}} = 5.95\text{ ns}$) in-order embedded core, worst-case $\text{CPI}_{\text{pipe}}$ sets the strict instruction ceiling $\text{IC}_{\max} \le T_{\text{deadline}} / (\text{CPI}_{\text{pipe}} \cdot T_{\text{clk}})$. Reducing $\text{CPI}_{\text{pipe}}$ from $1.68$ to $1.20$ via split SRAM banks and `-O2` scheduling expands the deterministic per-tick instruction budget from $100{,}000$ to $140{,}000$ instructions.

</Callout>

| Hazard Source | Condition / Policy | Global Stall Contribution ($f_i \times \text{Penalty}_i$) |
| :--- | :--- | :--- |
| **Structural (Memory)** | Unified single-port memory | $(f_{\text{load}} + f_{\text{store}}) \times 1$ |
| **Structural (Memory)** | Split Harvard `I-Cache` / `D-Cache` | $0$ |
| **Data (Forwarding ON)** | `ALU` $\to$ `ALU` / `Load` / `Store` ($k = 1, 2$) | $0$ |
| **Data (Forwarding ON)** | `Load` $\to$ `ALU` Load-Use ($k = 1$) | $f_{\text{load-use}} \times 1$ |
| **Data (Forwarding OFF)** | Any true `RAW` at $k = 1$ / $k = 2$ / $k \ge 3$ | $f_{k=1} \times 2 \;+\; f_{k=2} \times 1 \;+\; 0$ |
| **Control (Predict-Untaken)** | Resolved in `ID` ($1$) / `EX` ($2$) / `MEM` ($3$) | $f_{\text{branch}} \times p_{\text{taken}} \times P_{\text{stage}}$ |
| **Control (*Solo Stalli*)** | Resolved in `ID` ($1$) / `EX` ($2$) / `MEM` ($3$) | $f_{\text{branch}} \times 1.0 \times P_{\text{stage}}$ |
| **`ALU(i) -> Branch(i+1)`** | Forwarding ON, branch in **`ID`** | $f_{\text{ALU}\to\text{Branch}} \times 1$ |
| **`ALU(i) -> Branch(i+1)`** | Forwarding ON, branch in **`EX` or `MEM`** | $0$ (Decoy — ignore!) |

### Five-Step Exam CPI Procedure

1. **Start at Baseline $1.00$:** Verify that all instruction-mix percentages sum to $100\%$ ($1.00$).
2. **Evaluate $\text{Stalls}_{\text{struct}}$:** Add $(f_{\text{load}} + f_{\text{store}}) \times 1$ if unified memory is specified; write $0$ if split memories are specified.
3. **Evaluate $\text{Stalls}_{\text{data}}$:** Check whether forwarding is ON (count *only* distance-1 Load-Use $\times 1$) or OFF (count $k=1 \times 2$ and $k=2 \times 1$). Anchor each percentage carefully to its grammatical subject (producer vs. consumer).
4. **Evaluate $\text{Stalls}_{\text{ctrl}}$:** Pick $P_{\text{stage}} \in \{1, 2, 3\}$ (`ID`, `EX`, `MEM`), then multiply by $p_{\text{taken}}$ for Predict-Untaken or by $1.0$ for *solo stalli*.
5. **Check `ALU -> Branch` Interaction:** Add $f_{\text{ALU}\to\text{Branch}} \times 1$ **only** when branches resolve in stage `ID`; explicitly cross out `ALU -> Branch` when branches resolve in `EX` or `MEM`.

<Callout type="warning" title="Common Mistakes">

1. **Swapping Producer and Consumer Base Frequencies:** *"20% of ALU depend on Load"* is $f_{\text{ALU}} \times 0.20$, whereas *"20% of Load feed ALU"* is $f_{\text{Load}} \times 0.20$.
2. **Adding Decoy Stalls:** When forwarding is ON, write $= 0$ explicitly next to `ALU -> ALU` and (for `EX`/`MEM` branch resolution) `ALU -> Branch` in your written work so graders see deliberate filtering rather than an oversight.
3. **Comparing CPI Alone When $T_{\text{clk}}$ Differs:** Always multiply $\text{CPI}_{\text{pipe}} \times T_{\text{clk,pipe}}$ when comparing two pipelines with different stage delays or clock frequencies!

</Callout>

Common stall components across both configurations:

- **Unified Memory Structural Stalls:** $(0.20 + 0.10) \times 1 = 0.30$.
- **Load-Use Data Stalls (producer-relative to `Load`):** $0.20 \times 0.20 \times 1 = 0.04$.

   $$\text{Stalls}_{\text{ctrl,EX}} = 0.20 \times 0.50 \times 2 = 0.20$$
   $$\text{CPI}_{\text{EX}} = 1.00 + 0.30 + 0.04 + 0.20 + 0 = 1.54\text{ cycles/instr}$$
2. **Stage `ID` Branch Resolution ($P_{\text{ID}} = 1$, `ALU -> Branch` $= +1$):**
   $$\text{Stalls}_{\text{ctrl,ID}} = 0.20 \times 0.50 \times 1 = 0.10, \qquad \text{Stalls}_{\text{ALU}\to\text{Branch}} = 0.20 \times 0.25 \times 1 = 0.05$$

3. **Cycle Reduction:** Moving resolution to `ID` saves $1.54 - 1.49 = 0.05\text{ cycles/instr}$, reducing total cycles by $0.05 / 1.54 = 3.25\%$.

<summary>Reveal Worked Solution</summary>

1. **Clock Periods:**
   $$T_{\text{clk,single}} = 200 + 150 + 200 + 220 + 130 = 900\text{ ps}$$
   $$T_{\text{clk,pipe}} = \max(200, 150, 200, 220, 130) + 30 = 220 + 30 = 250\text{ ps}$$
2. **Unified-Memory Pipeline CPI and Net Speedup:**
   - $\text{Stalls}_{\text{struct}} = (0.18 + 0.12) \times 1 = 0.30$.
   - $\text{Stalls}_{\text{data}} = 0.55 \times 0.20 \times 1 = 0.11$ (`ALU -> ALU` forwarding $= 0$).
   - $\text{Stalls}_{\text{ctrl}} = 0.15 \times 0.60 \times 2 = 0.18$.
   - $\text{CPI}_{\text{pipe}} = 1.00 + 0.30 + 0.11 + 0.18 = 1.59\text{ cycles/instr}$.
   - Net speedup over single-cycle ($\text{IC} \gg 5$):
     $$S_{\text{pipe}} = \frac{1.00 \times 900\text{ ps}}{1.59 \times 250\text{ ps}} = \frac{900}{397.5} = 2.264\times$$
3. **Additional Speedup From Split L1 Caches (Amdahl's Law):**
   - Unified memory stalls account for $F_{\text{enh}} = 0.30 / 1.59 = 0.1887$ ($18.87\%$) of execution cycles; eliminating them ($S_{\text{enh}} \to \infty$) yields:
     $$S_{\text{Harvard}} = \frac{1}{1 - 0.30 / 1.59} = \frac{1.59}{1.29} = 1.233\times \quad (\text{raising total speedup over single-cycle to } 900 / (1.29 \times 250) = 2.791\times)$$

</details>
